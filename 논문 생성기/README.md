# 📄 SCI 논문 생성기

연구 주제·목적·방법·결과 메모를 입력하면, **4단계 파이프라인**을 거쳐 SCI(E)급 국제 학술지
투고 형식(IMRaD)에 맞춘 영문 논문 초안을 생성하고, **예상 심사위원 질문과 디펜스(답변) 초안**까지
준비해주는 시스템입니다.
KIAST R&D Architect와 동일한 아키텍처 패턴(FastAPI 백엔드 + 실시간 에이전트 모니터링 + HITL 승인 게이트)을 따릅니다.

파이프라인은 8개의 "역할"(전략 분석가·총괄 디렉터·집필가·인용 관리자·팩트체커·교정관·품질
감사관·동료 심사위원)을 수행하지만, 실제 코드는 **4개의 에이전트 클래스**(`strategist.py`,
`writer.py`, `reviewer.py`, `auditor.py`)로 정리되어 있습니다. 각 역할의 시스템 프롬프트와 생성
로직은 그대로 유지한 채 클래스만 합쳤기 때문에(로그에 찍히는 역할 이름도 동일), 출력 품질 저하
없이 파일 수만 절반으로 줄인 구조입니다.

## 핵심 원칙

- **지어내지 않는다.** 연구자가 제공하지 않은 데이터·통계·문헌은 절대 생성하지 않고
  `[NEEDS DATA: ...]`로 명시해 직접 채워 넣을 부분을 표시합니다.
- **단계마다 사람이 확인한다 (HITL Gate).** 아웃라인 승인(Gate 1) → 검증 결과 승인(Gate 2)을
  거쳐야 다음 단계로 진행되며, 매 단계에서 수정 요청/재생성이 가능합니다.
- **비용과 진행 상황이 투명하다.** 모든 API 호출의 토큰 사용량과 예상 비용을 실시간으로 기록·표시합니다.

## 4단계 파이프라인

| Phase | 내용 | 담당 역할 (구현 클래스) | 산출물 |
|---|---|---|---|
| 1. 기획 | 연구 갭 분석, 논문 논리 구조(배경→갭→목적→결론) 설계 | 총괄 디렉터 + 전략 분석가 (`StrategistAgent`) | 아웃라인 |
| **Gate 1** | 사용자가 아웃라인 검토·승인/수정/재생성 | — | 승인된 아웃라인 |
| 2. 초안 작성 | 섹션별 본문 집필, 참고문헌 포맷팅 및 인용 삽입 | 집필가 + 인용 관리자 (`WriterAgent`) | IMRaD 초안 |
| 3. 1차 검증 | 근거 부족 주장·재현성·윤리 정보 검증, 문장 명료성·약어 일관성 검토 | 팩트체커 + 교정관 (`ReviewerAgent`) | 이슈 리스트 |
| **Gate 2** | 사용자가 검증 결과 검토, 수정 요청 여부 결정 | — | 수정 반영된 초안 |
| 4. 최종 감사 | word limit·인용 교차검증·잔여 NEEDS DATA 등 최종 점검 + 종합 검토 + **예상 심사위원 질문/디펜스 생성** | 품질 감사관 + 동료 심사위원 (`AuditorAgent`) | 원고 DOCX + 체크리스트 리포트 + **리뷰어 Q&A 리포트** |

Phase 2와 Phase 3 사이에는 게이트가 없어 자동으로 이어집니다 (Gate 1 승인 → Phase 2·3 자동 실행 → Gate 2).
Gate 2 승인 시에도 Phase 4가 자동 실행되어 최종 파일이 생성됩니다.

### 예상 심사위원 Q&A (동료 심사위원 에이전트)

Phase 4에서 "Reviewer 2" 역할을 시뮬레이션하는 에이전트가 원고를 공격적으로 검토해 참신성·방법론·
통계·표본 크기·대안적 해석·일반화 가능성·재현성·윤리 등 실제 심사위원이 지적할 만한 구체적 질문
6~10개를 만들고, 각 질문에 대한 디펜스(답변) 초안을 작성합니다. **원고 데이터가 실제로 방어를
뒷받침하지 못하는 경우, 디펜스는 억지 반박을 지어내지 않고 한계를 정직하게 인정하도록 설계**되어
있습니다 (예: "We concede this limitation..."). `_reviewer_qa.docx`로 다운로드되며, 저자의 모의 디펜스
준비용 문서입니다 (제출용 아님).

## 다운로드 형식

완성된 **원고**는 DOCX / PDF / Markdown 세 가지 형식으로 각각 다운로드할 수 있습니다
(`backend/export/manuscript_export.py`). PDF는 reportlab으로 직접 생성하며, 국문(ko) 원고는
Noto Sans KR 서브셋 폰트(`backend/export/fonts/`, SIL OFL 1.1)를 임베드해 한글이 깨지지 않게
렌더링합니다. 체크리스트 리포트와 리뷰어 Q&A 리포트는 DOCX로만 제공됩니다(저자 작업용 문서라
서식 편집 편의성이 더 중요하다고 판단).

## 논문 유형 (자동으로 분량·구조·강조점이 달라짐)

| 유형 | 목표 분량 | 구조 특징 |
|---|---|---|
| Original Research Article (기본값) | 4,000~7,000단어 (15~25페이지) | IMRaD 전체 구성, 참신성·재현성 강조 |
| Short Communication / Letter | 1,500~3,000단어 (4~8페이지) | Results+Discussion 통합, 핵심 메시지 하나에 집중 |
| Review Article | 6,000~10,000단어 (25~40페이지) | 주제별 소단원 구성, 문헌 비판적 종합 |

## 작성 언어 (English / 한국어)

입력 폼의 "작성 언어"에서 선택합니다.

- **English (기본값)**: SCI(E) 국제 학술지용. 4개 에이전트 전부 영문으로 작성.
- **한국어**: KCI 등 국내 학술지 작성 관례에 맞춰 전부 국문으로 작성 (전문용어는 "한글 용어(English term)" 형태로 병기). 시스템 프롬프트의 콘텐츠 규칙(논리 구조, 근거 없는 내용 금지, 인용 규칙 등)은 언어와 무관하게 동일하게 적용되고, 출력 언어 지시문만 교체됩니다 (`backend/agents/language_utils.py`). 원고 DOCX는 한글이 깨지지 않도록 맑은 고딕 폰트로 자동 전환됩니다.

두 언어 모두 실제 API 호출로 전체 파이프라인(Gate 1→2→완료, DOCX 3종 생성)을 검증했습니다.

## 폴더 구조

```
논문 생성기/
├── backend/
│   ├── main.py              # FastAPI 서버 (REST + SSE 실시간 로그)
│   ├── config.py            # GEMINI_API_KEY(.env 공유), 모델, 논문 유형별 설정
│   ├── agents/               # 4개 에이전트 클래스 (base_agent.py가 공통 Gemini 호출 담당)
│   ├── pipeline/              # phase1~4 파이프라인 오케스트레이션
│   ├── db/                   # SQLite: 세션/이벤트로그/토큰사용량
│   └── export/                # DOCX/PDF/Markdown 생성기 + fonts/(한글 PDF용 Noto Sans KR)
├── frontend/                  # index.html + app.js + style.css
├── data/                      # SQLite DB 파일 (자동 생성)
├── output/                    # 생성된 DOCX 파일 (자동 생성)
├── .env                       # GEMINI_API_KEY (직접 생성, git에 포함 안 됨)
└── start.sh                   # 실행 스크립트
```

## 실행 방법

```bash
cp .env.example .env   # 최초 1회 — .env를 열어 GEMINI_API_KEY 입력
chmod +x start.sh
./start.sh
```

이미 다른 프로그램(예: 이메일 분석기, KIAST R&D Architect)에서 `GEMINI_API_KEY`를 쓰고 있다면
그 `.env`를 그대로 복사해서 재사용해도 됩니다 (같은 Google API 키를 여러 프로그램이 공유하는 구조).

브라우저가 자동으로 `http://127.0.0.1:8010` 을 엽니다. 수동 실행:

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cd backend && python main.py
```

API 문서(Swagger UI)는 `http://127.0.0.1:8010/docs` 에서 확인할 수 있습니다.

## 모델 / 비용

- 기본 모델은 비용 절감을 위해 전 Phase `gemini-flash-latest`로 통일되어 있습니다
  (`backend/config.py`의 `GEMINI_PRIMARY_MODEL`/`GEMINI_FAST_MODEL`).
- `.env`에 `GEMINI_PRIMARY_MODEL=gemini-pro-latest`를 추가하면 Phase 1~3(기획/초안/검증)의
  품질을 높일 수 있습니다 (비용은 약 4배 증가).
- 논문 한 편(Original Research, 수정 1회 포함) 생성 비용은 실측 기준 **$0.05~0.10** 수준입니다.
  화면 상단 배지에서 실시간으로 API 호출 횟수·토큰·비용을 확인할 수 있습니다.

## 알려진 제약사항

- **개발 서버 재시작 중 SSE 연결 문제**: `backend/` 코드를 수정하면 `--reload`가 서버를 재시작하는데,
  이때 브라우저에 실시간 로그 스트림(SSE)이 연결되어 있으면 재시작이 멈출 수 있습니다.
  파이프라인이 진행 중일 때는 코드를 수정하지 말고, 만약 멈추면 서버를 완전히 재시작하세요.
- **표절 검사 미포함**: 이 프로그램은 외부 문헌 데이터베이스 대조 표절 검사(Turnitin, iThenticate 등)나
  자기표절 검사를 수행하지 않습니다. 투고 전 소속 기관의 표절 검사 도구를 반드시 사용하세요.
- **재현성 통계 사전 신뢰 아님**: 잔여 `[NEEDS DATA: ...]` 표시나 재현성 이슈는 팩트체커가 연구자의
  원문 메모만 근거로 판단한 것으로, 실제 통계 검증을 대체하지 않습니다.
- **간헐적 생성 실패**: Gemini가 드물게 빈 응답이나 불완전한 JSON을 반환하는 경우가 있습니다. 이 경우
  해당 Phase가 명확한 오류 메시지와 함께 실패로 표시되며(예전처럼 조용히 빈 결과로 진행되지 않음),
  Gate 화면에서 "전체 재생성" 버튼으로 재시도하면 됩니다.

## 주의사항

이 프로그램이 생성하는 초안은 **작성 보조 도구**입니다. 실제 투고 전 반드시 연구자 본인이 데이터
정확성, 통계 검증, 표절 여부, 목표 저널의 투고 규정(Author Guidelines)을 직접 확인해야 합니다.
체크리스트 리포트(`_checklist.docx`)와 리뷰어 Q&A 리포트(`_reviewer_qa.docx`)는 저널에 제출하는
문서가 아니라 저자 본인의 작업용 참고 문서입니다. 특히 Q&A의 디펜스 문구를 실제 리뷰어 답변에
그대로 옮기기 전에, 진짜 한계를 인정한 부분과 실제 반박이 가능한 부분을 반드시 직접 검토하세요.
